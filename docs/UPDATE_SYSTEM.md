# NexaDrive Update System

How NexaDrive updates itself: the Update Center in the app, the release manifest, the CI pipeline that produces both, and the security model behind them.

---

## 1. Overview

```
Check              Compare           Download              Install
─────────────      ─────────────     ────────────────      ────────────────────
Update Center  →   SemVer 2.0.0  →   streamed to app   →   platform installer
fetches the        (never lexico-    cache; SHA-256        (APK installer, Inno
manifest from      graphic; prere-   verified in-          Setup, AppImage
GitHub Releases    leases sort       stream; size and      swap, or package
                   lower)            checksum enforced     manager)
```

The update system is **independent of the NexaDrive server**: the client talks directly to GitHub Releases, so a downed NexaDrive server never blocks an application update. No server credentials, account data, or file names are ever sent to the update service — the check is a single anonymous HTTPS GET for the manifest.

Entry point: **Settings → About → Update center**, with a subtle indicator tile in Settings when an update is available. There is no persistent polling; a silent check runs at most once per 24 h, and the manual button always works.

## 2. Release manifest

Every tag release publishes `nexadrive-update-manifest.json` as a release asset. Generated by `scripts/update-manifest.sh`; verified by `scripts/verify-update-manifest.py` and by the client's `UpdateManifest.fromJson`.

### Schema (v1)

```json
{
  "version": "1.3.0",
  "tag": "v1.3.0",
  "releaseDate": "2026-09-14T12:00:00Z",
  "prerelease": false,
  "minimumSupportedVersion": null,
  "minimumServerVersion": "1.2.0",
  "serverApiVersion": "1.0.0",
  "releaseNotes": {
    "What's new": ["Headline feature"],
    "Bug fixes": ["Fix sync stall on flaky networks"]
  },
  "artifacts": {
    "android": {
      "arm64-v8a": {
        "apk": { "url": "https://github.com/.../NexaDrive-1.3.0.apk", "sha256": "<64 hex>", "size": 48123864 }
      }
    },
    "windows": {
      "x64": {
        "installer": { "url": "https://github.com/.../NexaDrive-1.3.0-windows-x64-setup.exe", "sha256": "<64 hex>", "size": 22118400 },
        "zip": { "url": "https://github.com/.../NexaDrive-1.3.0-windows-x64.zip", "sha256": "<64 hex>", "size": 23068672 }
      }
    },
    "linux": {
      "x64": {
        "appimage": { "url": "https://github.com/.../NexaDrive-1.3.0-linux-x86_64.AppImage", "sha256": "<64 hex>", "size": 94371840 },
        "deb": { "url": "https://github.com/.../NexaDrive-1.3.0-linux-amd64.deb", "size": 88901509, "sha256": "<64 hex>" }
      }
    }
  }
}
```

Field rules (enforced on both sides — generator and client):

| Field | Rule |
| --- | --- |
| `version` | SemVer 2.0.0, `MAJOR.MINOR.PATCH[-prerelease]`, tag = `v` + version |
| `releaseDate` | ISO-8601 UTC, ends in `Z` |
| `prerelease` | boolean; must be `true` iff version carries a prerelease identifier |
| `minimumSupportedVersion` | null or SemVer ≤ `version`; when newer than the installed version the update is **mandatory** |
| `minimumServerVersion` | null or SemVer; the oldest server release this client can talk to. When set, the Update Center compares against `GET /api/server/status` → `version` and warns the user if their server is older |
| `serverApiVersion` | null or string (SemVer); the server's API surface contract. Stored for future server/client negotiation; currently informational |
| `releaseNotes` | object of `section → list of strings`; rendered as inert plain text (control characters and HTML stripped) |
| `artifacts.<platform>.<arch>.<kind>` | `url` (HTTPS, github.com only), `sha256` (64-hex), `size` (positive int, bytes) |

- Platforms: `android`, `windows`, `linux`. Arch keys: `arm64-v8a` / `armeabi-v7a` / `x86` / `x86_64` (Android ABIs), `x64` / `aarch64` (desktop).
- One universal APK is published; the same entry is keyed under every Android ABI.
- Windows ships both `installer` (Inno Setup .exe) and `zip` (portable layout). The Update Center uses `installer` for installed copies and `zip` for portable copies.

### Client validation

Before anything is trusted, the client rejects a manifest that: is not valid JSON, misses required fields, carries a non-SemVer version, embeds a 64-hex-invalid or wrong-length checksum, declares a size ≤ 0, points at a non-HTTPS or non-github.com URL, or declares `minimumSupportedVersion` newer than the release itself.

## 4. Platform install flows

### Android (APK)

1. The verified APK is downloaded into the app-private cache (`<cache>/nexadrive_updates/`).
2. The app hands the file to the **system package installer** through a `FileProvider` content URI — never a raw filesystem path. No silent install, no root, no modified security settings.
3. The user confirms in the stock install dialog. If Android blocks the source, the Update Center switches to a *permission needed* state, explains it, and deep-links to **Settings → Install unknown apps** for this app (per-source consent — not a global security disable).
4. On return to the app, reconciliation compares the installed version with the manifest; completion is only declared when the OS reports the new version.
5. Signing: the release APK must be signed with the production keystore; tag CI **fails** without `KEYSTORE_BASE64`. Same application ID (`io.nexadrive.app`) + same signing cert are what make Android accept the install as an upgrade.

### Windows (Inno Setup installer)

1. `NexaDrive-<ver>-windows-x64-setup.exe` is downloaded and verified.
2. The app launches it detached and hands over to the user. Windows handles any elevation prompt; the app never escalates.
3. The Inno Setup installer (`app/windows/installer/nexadrive.iss`) installs per-user (`PrivilegesRequired=lowest`), creates Start Menu / optional desktop shortcuts, upgrades in place without touching user data, and uninstalls cleanly. It never contains server data.

### Windows (portable ZIP)

1. `NexaDrive-<ver>-windows-x64.zip` is downloaded and verified.
2. The ZIP is unpacked into a staging directory (`.nexadrive-stage-<ts>`) next to the running app. CRC integrity and path-traversal guards are applied to every entry; only `nexadrive.exe` and `data/` content is accepted.
3. A `nexadrive-finish-update.cmd` helper is written into the same stage directory. This helper waits for the running `nexadrive.exe` to exit, then uses `xcopy /Y /E` to swap the files, relaunches the app, and self-deletes.
4. The helper is launched via `Process.start(..., mode: ProcessStartMode.detached)`. The Update Center switches to *installingHandoff*: "Download complete — restart NexaDrive to finish the update."
5. If the helper cannot be started, the Update Center falls back to *readyToInstall* with the same user message and the verified file path.
6. The running executable is never deleted or overwritten in place; this is a hard OS constraint for portable Windows apps.

### Linux — AppImage

1. If `$APPIMAGE` is set (running as an AppImage) and its folder is writable: stage copy → `chmod +x` → old image renamed aside → staged image atomically `rename(2)`d over the live path → backup dropped. The running binary keeps working throughout; a failure rolls back to the original image.
2. If the folder is not writable, the Update Center says so plainly and offers the verified file for manual replacement — no mysterious failure.

### Linux — .deb

1. The verified .deb is downloaded; the app **never** runs `sudo` or embeds credentials.
2. The Update Center shows the install command (copyable) and offers to open the package with the system installer where the desktop environment supports it.
3. Privileged installation is left to the user's package manager.

### Detecting how the client itself is installed

The updater must pick the right installer per copy of the app:

| Platform | Detect | Decides |
| --- | --- | --- |
| Windows | `LOCALAPPDATA\Programs`, `Program Files`, `Program Files(x86)`, or an `unins*.exe` / "Uninstall NexaDrive.exe" next to the running exe → **installed**; otherwise → **portable** | installer (.exe) vs zip (portable) |
| Linux | `$APPIMAGE` set → **appimage**; binaries under `/usr/lib/nexadrive` / `/usr/bin/nexadrive` and `dpkg -s nexadrive` → **deb**; otherwise → **source/unknown** | AppImage vs .deb package |
| Unknown | — | Update Center shows "Choose your Linux package" (AppImage / .deb). User's pick is remembered via `chooseLinuxPackage`. |

A development/source build reports "You are running a development/source build…" and never contacts the network.

## 5. Download engine

- **Streaming**: bytes are written to a `.part` file as they arrive and hashed incrementally; nothing large is held in memory.
- **Verification before commit**: the `.part` file is renamed to its final name only after the size **and** SHA-256 match the manifest. A mismatch deletes the partial and reports `checksum mismatch`.
- **Redirect safety**: every redirect hop is re-validated against the HTTPS github.com allowlist (`_SafeRedirectClient`).
- **Cancellation**: mid-stream cancel aborts, deletes the partial, and returns to the pre-download state (a mandatory release stays mandatory).
- **Retry**: transient network/HTTP failures retry with backoff; permanent failures surface actionable errors.
- **Cache bounds**: `UpdateCache.prune()` (runs on app start and after a completed update) keeps the update cache under 300 MB and 21 days, removing old installers and stale partials. Files live in the platform's app-private temp/cache dir — never in NexaDrive user storage or server data.

## 6. Security model

- **HTTPS everywhere**: manifest and artifacts; TLS validation is never disabled, and the shared `http` stack is reused — no second insecure client.
- **Official source only**: manifest and artifact URLs must be `https://` on `github.com` / `*.githubusercontent.com`. Arbitrary URLs are rejected; redirects to other hosts downgrade to rejection.
- **SHA-256 integrity**: every artifact's digest is embedded in the manifest and recomputed during download. A mismatched artifact is never executed or installed.
- **No privilege escalation**: no sudo, no root, no silent install, no security-setting changes; installers run with the user's privileges and the OS prompts for elevation where needed.
- **Path safety**: artifact file names are sanitized to flat basenames (no separators, no traversal); downloads land in fixed app-private directories.
- **Server version compatibility**: `minimumServerVersion` / `serverApiVersion` in the manifest are compared against `GET /api/server/status`. The Update Center warns the user (never silently blocks) when the running server is too old.
- **Inert release notes**: notes are sanitized plain text (control chars and HTML stripped), rendered as bullets — no markdown/HTML execution.
- **Privacy**: the update check sends nothing but the manifest request; no user identity, server URL, tokens, or usage data. See `docs/SECURITY.md` for the wider model and `SECURITY.md` for reporting.

### Threat model highlights

| Threat | Mitigation |
| --- | --- |
| Compromised release metadata | Manifest accepted only from the official repo over HTTPS; every digest re-verified against the actual bytes |
| MITM / downgrade to HTTP | TLS only; redirect hops re-validated; non-HTTPS rejected |
| Wrong/mismatched artifact | Exact platform + arch selection, no fuzzy fallback; size + SHA-256 must match |
| Malicious filename / traversal | Filenames sanitized to basenames; fixed cache directories |
| Partial download | `.part` file committed only after verification; interrupted downloads cleaned |
| Disk exhaustion | 300 MB / 21-day bounded cache with pruning |
| Installer replacement | Verified installer launched from the app-private cache; APK handed off via FileProvider content URI |
| Privilege escalation | No automatic sudo/root; OS handles elevation; per-user installers |
| Malicious release notes | Sanitized to plain text; never rendered as HTML |

**Downgrades**: a release older than the installed version is never offered. A forced downgrade path, if ever needed, would be a separate developer workflow outside the Update Center.

**Known residual risk**: the trust root is the GitHub repository and its release signing material. If the GitHub account or the Android keystore is compromised, technical client-side checks cannot save you — protect them (2FA, restricted tokens, keystore custody). The client's checksum pinning detects corrupted or truncated downloads and any artifact swapped after the manifest is generated.

## 7. CI/CD release flow

Pushing `vX.Y.Z` triggers `.github/workflows/release.yml`:

1. **Verify source**: version consistency (Cargo.toml ↔ pubspec.yaml ↔ git tag), gitleaks, Rust checks, `flutter analyze` + `flutter test`.
2. **Build**: server x86_64 + aarch64, Android APK, Linux AppImage + deb, Windows zip + Inno Setup installer.
3. **Android gate**: tag builds **fail** without the release keystore — a debug-signed APK can never install as an upgrade.
4. **Checksums**: `SHA256SUMS.txt` is generated for every platform artifact and each is re-verified (`sha256sum --check --strict`). The manifest is **excluded** from the list: the finalize step merges real release notes back into it and re-uploads it, which would leave a stale digest. The manifest is self-verifying instead — `verify-update-manifest.py` re-checks every embedded URL/digest against disk before and after finalize.
5. **Manifest**: `scripts/update-manifest.sh` generates `nexadrive-update-manifest.json` from the actual artifacts; `scripts/verify-update-manifest.py` re-checks schema, HTTPS-allowlisted URLs, sizes, and digests against disk. Any mismatch fails the release.
6. **Publish**: GitHub release with all artifacts, `SHA256SUMS.txt`, and the manifest. The finalizer then parses the published release notes into the manifest's structured `releaseNotes` and re-uploads it.
7. The Update Center consumes exactly the artifacts CI produced — no hand-maintained URLs anywhere.

Manual `workflow_dispatch` builds (pre-release testing) skip the manifest, never create a GitHub Release (the release and finalize steps are gated to `github.ref_type == 'tag'`), and allow a debug-signed APK; the client only consumes manifests from real tag releases.

## 8. Testing

- `app/test/update/` — 97+ tests: SemVer precedence, manifest parsing/validation, platform/arch/installation-kind selection, download engine (checksum mismatch, size mismatch, cancellation, redirects, stale-download abort), controller state machine (check policy, mandatory vs optional, cancel-during-mandatory, install hand-off, reconciliation, portable-zip Windows flow, Linux source-build rejection, server-version compatibility), stall regression tests (body read timeout, idle download watchdog), offline/HTTP failure mapping, and cache policy.
- `scripts/update-manifest.sh` and `scripts/verify-update-manifest.py` are exercised in CI on every release; negative cases (tampered checksum, missing artifact, version/tag mismatch) fail the release.
- `server/src/main.rs` has 21 tests; `cargo test` + `cargo clippy` run in CI.
- Integration flows (check → download → verify → hand-off) run against mocked HTTP; CI never depends on live GitHub availability.

Before the first public release, run one real end-to-end flow against a test/pre-release artifact (metadata → download → checksum → install hand-off) without touching a production installation.

## 9. Troubleshooting

| Symptom | Meaning / fix |
| --- | --- |
| "No internet connection" | Offline, or the endpoint was unreachable. Retry with **Try again**; no background retries run. |
| "The update server returned HTTP …" | GitHub-side problem or rate limiting. Wait and retry; silent checks back off for 24 h. |
| "No installer is published for this device" | Release lacks an artifact for your platform/arch. Wait for a fixed release. |
| "The download failed verification (SHA-256 mismatch)" | Corrupted/truncated download (or tampered metadata). Retry; the bad file is deleted automatically. |
| "Insufficient storage" | Free space in the app cache location; the updater needs roughly the artifact size. |
| Android: "Permission needed" | Grant **Install unknown apps** for NexaDrive via the in-app button, then tap Install again. |
| Android: "App not installed" after the dialog | The build was not signed with the same key as the installed app (or the ABI doesn't match). Check signing identity and application ID. |
| Linux AppImage: "folder is not writable" | Move the AppImage to a writable folder (e.g. `~/Applications`) or run with appropriate permissions. |
| Linux .deb: nothing installed | The updater never uses sudo. Run the shown command in a terminal, or open the package with the system installer. |
| Windows: installer didn't appear | Launch the verified file manually from the shown cache path. |
| Windows: portable update handoff didn't run | Restart NexaDrive; the `nexadrive-finish-update.cmd` helper will detect the staged files and complete the swap. Alternatively, extract the `.nexadrive-stage-*` folder over the app directory manually. |
| "This release needs a newer server" | Your server version is older than `minimumServerVersion` in the manifest. Update the server binary before installing the app update. |
| Update succeeded but version didn't change | Fully exit and relaunch NexaDrive; the About dialog shows the running version. |

## 10. Developer workflow

```bash
# 1. Bump versions together (release-verify enforces agreement):
#    app/pubspec.yaml, server/Cargo.toml
# 2. Update CHANGELOG.md.

# 3. Tag and push:
git tag vX.Y.Z && git push origin vX.Y.Z

# CI builds, verifies, and publishes everything, including the manifest.

# Local pre-release test of the manifest pipeline:
flutter build linux --release
scripts/package-linux.sh X.Y.Z dist
# ...produce the other artifacts or stub them, then:
scripts/update-manifest.sh X.Y.Z 0 dist
python3 scripts/verify-update-manifest.py dist/nexadrive-update-manifest.json
```

Override the release repository for testing with `NEXADRIVE_RELEASE_REPO` (manifest generation) and `--dart-define=NEXADRIVE_UPDATE_REPO=owner/repo` (client). Point both at a private test repo to exercise a real end-to-end update without touching production.
